## 0. Doctrine définitive (Patrick, 20/09/2026)

> « Vente ≠ encaissement. Une vente à crédit compte dans l'activité commerciale, crée une créance et décrémente le stock, mais ne rentre pas dans la caisse. Son règlement ultérieur est un encaissement lié à cette créance et ne crée jamais une nouvelle vente. »

Corollaires tenus dans tout ce document :

- les agrégats distinguent **explicitement** quatre familles : **ventes** (activité commerciale), **encaissements** (argent entré dans la boîte), **créances** (ce qui est dû), **règlements** (encaissements liés à une créance) ;
- **aucun double comptage de CA** : une vente à crédit est UNE vente, comptée une fois, dans les ventes ; son règlement n'est jamais une seconde vente ;
- le défaut n'est pas `type='vente'` — c'est chaque lecteur qui prend `type='vente'` pour « argent encaissé ».

Vocabulaire de classification utilisé dans les tableaux :

| Classe | Définition | Lignes `caisse_transactions` concernées aujourd'hui |
|---|---|---|
| **vente commerciale** | activité, chiffre d'affaires, volume vendu | `type='vente'`, tout `mode_paiement` |
| **encaissement** | argent physiquement entré (espèces ; mobile money : voir D-6) | `type='vente'` avec `mode_paiement<>'credit'` + `type IN ('acompte_credit','reglement_credit')` |
| **créance** | dette ouverte d'une cliente | table `credits` / `clients.montant_du` — **aucune ligne** de `caisse_transactions` |
| **règlement** | encaissement lié à une créance | `type IN ('acompte_credit','reglement_credit')` |
| **mixte** | un lecteur qui mélange deux familles sous un seul nombre | à scinder |

## C. Conception proposée (décisions 1 à 4) — à coder plus tard, par commits isolés

### C-0 Règle transversale : une nature dérivée, lue par tous

Aujourd'hui la famille d'une ligne se déduit de deux chaînes libres (`type`, `mode_paiement`) et chaque lecteur refait la déduction (B2 seul la fait bien). Proposition : une **fonction SQL immuable** `nature_caisse(type, mode_paiement)` → `'vente_encaissee' | 'vente_credit' | 'reglement' | 'depense' | 'autre'`, posée par DbInit (`CREATE OR REPLACE FUNCTION`, idempotente, 0 colonne), utilisée par tous les agrégats backend ; côté téléphone, l'équivalent `natureCaisse(tx)` dans `statsVente.ts` (F9). Alternative avec colonne : `caisse_transactions.nature varchar(24)` remplie à l'écriture (+1 colonne, +1 CHECK) — plus lisible dans les exports (B16), mais duplique une information dérivable ; **je propose la fonction**, la colonne reste une option (D-8).

### C-1 Annulation d'une vente à crédit (ARG-13)

Règle : `PATCH …/annuler` et `PATCH /transactions/:id` (statut → `annulee`) passent par **une primitive partagée** `annulerVente(manager, tx, motif, acteur)` (même patron que `restituerStock` / `vente-stock.ts`) :

1. si `tx.mode_paiement <> 'credit'` : comportement actuel (statut, motif, ledger) ;
2. sinon, lire `credits WHERE transaction_id = tx.id FOR UPDATE` ;
   - **aucun règlement** (aucune ligne `acompte_credit`/`reglement_credit` liée, et `credits.acompte = 0`) ⇒ **annulation atomique** dans la même transaction : `caisse_transactions.statut='annulee'` + `motif` ; `restituerStock` (ledger inverse, historique conservé) ; `credits.statut='annule'`, `credits.annule_le=now()`, `credits.annulation_motif` ; `clients.montant_du = GREATEST(0, montant_du − montant_total)` ; `audit_logs` `CREDIT_ANNULATION`. Aucune ligne n'est supprimée ;
   - **un règlement existe** ⇒ **refus** `409 { code: 'CREDIT_DEJA_ENCAISSE' }`, rien n'est écrit ; le message nomme le flux à utiliser : « avoir sur créance / remboursement » (**hors lot**, C-8).
3. La vue `credits_avec_statut` doit rendre `statut='annule'` et `montant_restant=0` pour un crédit annulé (sinon le carnet continuerait d'afficher la dette).

Colonnes nouvelles : `credits.annule_le timestamptz NULL` (+1), `credits.annulation_motif text NULL` (+1) ; la vue expose `annule_le` (+1 colonne de vue). Index : `idx_credits_transaction ON credits(transaction_id)` (0 colonne). Lien règlement → créance : voir C-3 (`caisse_transactions.credit_id`).

Invariants (`blockers.spec.ts` ou `arg-13-annulation-credit.spec.ts`) : **ANN-1** vente à crédit sans règlement annulée par la marchande ⇒ vente `annulee`, crédit `annule`, `montant_du` revenu, stock restitué, lignes conservées, rejeu idempotent (net du ledger) ; **ANN-2** après un acompte ⇒ 409, `SELECT` avant/après identiques (vente, crédit, client, stock, ledger) ; **ANN-3** même règle par le chemin admin ; **ANN-4** une vente espèces s'annule comme avant (non-régression `annulation-remise-stock.spec.ts`) ; **ANN-5** un crédit annulé n'est plus encaissable (`/acompte` ⇒ 400).

### C-2 Identité de la cliente (CLIENT-02)

- `clients.id` est l'identité ; **toute nouvelle vente à crédit porte `credits.client_id`** (colonne déjà posée, nullable pour l'historique — le code et un invariant l'exigent sur les nouvelles lignes ; pas de `NOT NULL` en base, qui interdirait l'historique).
- `credits.client_nom` **est** le `nom_snapshot` (nom au moment de la vente) : on le documente, on ne le renomme pas, on n'ajoute pas de colonne (0 colonne).
- Création : `client_id` fourni ⇒ cette cliente (`FOR UPDATE`, même marchande, 404 sinon — sans révéler l'existence d'une cliente d'autrui) ; absent ⇒ **création d'une nouvelle cliente dans la même transaction**, jamais d'upsert par nom. Deux homonymes = deux personnes.
- Schéma : lever `ux_clients_marchand_nom` (index unique `(marchand_id, nom)`, DbInit l. 647) → index **non unique** `idx_clients_marchand_nom` ; l'`ON CONFLICT (marchand_id, nom)` disparaît de `creer-credit.ts`. 0 colonne. Migration miroir : point d'intégration C.
- Routes : `GET /caisse/credits/clients` (existe, 10 récentes) ; nouvelle `GET /caisse/credits/clients/:id` ; `GET /caisse/credits/clients/:nom` (`ILIKE`) devient une recherche `?q=` et ne sert plus d'identité ; `GET /caisse/credits` expose `client_id` (déjà dans la vue).
- Téléphone (gelé, à faire avant activation) : `CreditModal` choisit dans la liste (envoie `client_id`) ou dit « nouvelle cliente » ; `caisse-api.ts:CreerCreditData` : `client_id?`, commentaire de `idempotency_key` corrigé.
- Invariants : **CLIENT-02 promu** (deux homonymes, téléphones différents ⇒ deux clientes, deux dettes) ; **CLIENT-03** `client_id` d'une autre marchande ⇒ 404 sans écriture, message identique à « introuvable » ; **CLIENT-04** anciennes lignes `client_id NULL` lisibles et encaissables par le nom (existe : « repli ») ; **CLIENT-05** rejeu même clé sans `client_id` ⇒ une seule cliente ; **CLIENT-06** deux créations simultanées de la même nouvelle cliente avec deux clés ⇒ deux clientes (assumé : c'est le choix « nouvelle cliente » qui est répété).

### C-3 Idempotence scopée par marchande (ARG-15, décision 3)

- Index : remplacer `ux_caisse_tx_idempotency_key (idempotency_key)` (DbInit l. 216-220, migration archivée `1778700200000`) par `ux_caisse_tx_marchand_idempotency (marchand_id, idempotency_key) WHERE idempotency_key IS NOT NULL` (0 colonne ; `DROP INDEX IF EXISTS` + `CREATE UNIQUE INDEX IF NOT EXISTS`, idempotent ; le test « second démarrage » du gate le vérifie). `credits` est déjà scopé.
- Lectures : `encaisserCredit` l. 122-125 ajoute `AND marchand_id = $2` ; `transactionExistante` (W1) filtre déjà `user_id`.
- Clés dérivées (`credit-vente-<clé>`, `credit-creation-<clé>`, `credit-acompte-<clé>`, `credit-reglement-<clé>`) restent : elles n'entrent plus en collision entre marchandes.
- **409 = même marchande, même clé, charge métier différente** : stocker un condensé canonique `idempotency_hash varchar(64) NULL` sur `credits` (+1) et `caisse_transactions` (+1) — SHA-256 de la liste **explicite** des champs métier (crédit : `client_id|client_nom`, `montant_total`, `acompte`, `echeance`, articles normalisés ; vente : `montant`, `mode_paiement`, lignes normalisées ; encaissement : `credit_id`, `montant`). Rejeu : hash égal ⇒ même réponse ; hash différent ⇒ `409 { code: 'IDEMPOTENCE_CHARGE_DIFFERENTE' }` sans écriture. Le QA-B (A4) a observé « la clé gagne » : cela devient un 409. Alternative sans colonne : comparer champ à champ — fragile sur `articles` ; **je propose le hash**.
- Lien règlement → créance : `caisse_transactions.credit_id uuid NULL` (+1), rempli par `encaisserCredit` ; index `idx_caisse_tx_credit`. Il remplace la déduction par description et rend C-1 (« un règlement existe ? ») et B6/B12 (`creances`, `reglements`) triviaux.
- Aucune erreur ne révèle une autre marchande : avec l'index scopé, la même clé chez deux marchandes ⇒ deux écritures indépendantes (201/201) ; les 404/409 ne citent jamais un identifiant étranger.
- Invariants : **IDEM-1** deux marchandes, même clé brute ⇒ 201/201, deux crédits, deux ventes ; **IDEM-2** même marchande, même clé, même charge ⇒ rejeu (`rejeu:true`, aucune écriture) ; **IDEM-3** même clé, charge différente ⇒ 409, aucune écriture ; **IDEM-4** idem pour `/acompte` ; **IDEM-5** `/caisse/vente` (I2 étendu : clé scopée, charge différente ⇒ 409) ; **IDEM-6** le rejeu d'une vente à crédit ne retranche pas le stock deux fois (existe : I6b).

### C-4 Datation hors ligne (décision 4, ARG-14)

- Deux temps : `caisse_transactions.occurred_at timestamptz NULL` (+1) = moment métier (téléphone, `date_operation`) ; `created_at` = réception serveur, **ne bouge plus** (aujourd'hui W1/W2 écrasent `created_at` : une seule colonne, deux sens). Historique : `occurred_at NULL` ⇒ les lecteurs lisent `COALESCE(occurred_at, created_at)` ; aucune réécriture.
- `credits.occurred_at timestamptz NULL` (+1, recommandé) : le jour de la créance est celui de sa vente ; sans cette colonne, le carnet devrait joindre `caisse_transactions` pour dater (`AppContext.creditsJour` lit `credits.created_at`). Option : dériver par `transaction_id` (0 colonne) — D-3.
- Règle déterministe (`date-operation.ts`, bornes +10 min / −14 j conservées) : hors bornes ou illisible ⇒ **400 `{ code: 'DATE_OPERATION_INVALIDE', min, max }`**, rien n'est écrit — fin de la correction silencieuse (l. 20). La file hors ligne classe l'opération en lettre morte **visible** (`incidentsHorsLigne.ts`, `SyncEchecsBanner`) : la marchande voit qu'une vente n'est pas passée et pourquoi.
- Le timestamp client n'est **jamais** preuve d'autorisation ni d'idempotence : l'autorisation vient du jeton, l'idempotence de la clé + hash (C-3) ; `occurred_at` n'entre pas dans le hash (D-3) sinon un même rejeu daté différemment ferait 409.
- Journée : `ensureSessionOuverte(marchandId, occurred_at::date)` — la vente rejouée rejoint la journée où elle a eu lieu ; la clôture d'une journée passée n'est pas rouverte (règle existante : « rouvrir reste permis » — à confirmer pour une journée **fermée**, D-3). `caisseTheorique(jour)` et tous les lecteurs « jour » (B2, B3, B6-B12, F1-F8 via `date ← occurred_at`) basculent sur `COALESCE(occurred_at, created_at)`.
- Vente à crédit : `CreerCreditDto.date_operation?` ⇒ `occurred_at` de la vente, de la créance et de l'acompte initial.
- Invariants : **DATE-1** vente rejouée avec `date_operation = J−1` ⇒ `occurred_at = J−1`, `created_at = aujourd'hui`, rattachée à la session J−1, comptée dans `caisseTheorique(J−1)`, pas dans celle du jour ; **DATE-2** date > +10 min ⇒ 400, rien écrit ; **DATE-3** date < −14 j ⇒ 400 ; **DATE-4** deux envois même clé, dates différentes ⇒ rejeu (la date n'est pas la charge) ; **DATE-5** vente à crédit datée ⇒ vente, créance, acompte au même jour métier ; **DATE-6** `created_at` d'une ligne rejouée n'est jamais dans le passé.
