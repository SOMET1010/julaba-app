## 3. Points forts

### Top 5 points forts du projet

1. **Souveraineté vocale** : STT sherpa-onnx + TTS VITS-Piper embarqués nativement dans l'APK (150 Mo total) — aucune dépendance cloud pour la boucle vocale, fonctionne hors-ligne dès le 1er jour. Cas d'école pour les marchés à faible connectivité.

2. **Sécurité financière défense en profondeur** : idempotence systématique sur tous les mouvements d'argent (wallet_transactions, caisse_transactions, fidelite_evenements, stock_operation), verrous pessimistes `pessimistic_write` sur Wallet, `assertCompteActif` dans la même transaction, fail-closed partout (InstitutionScopeGuard, rolesCreablesPar, OdooRealClient allow-list), sanitization triple couche (ClassSerializerInterceptor + stripSensitiveUserFields + @Exclude).

3. **Gouvernance exemplaire pour un pilote** : Constitution formalisée avec 8 principes + mécanismes CI actionnables (anti-doublon, ADR obligatoire, DoD, modules sacrés, invariants testables), 5 ADR standardisés, registre de dette à 20 révisions avec auto-correction documentée (l'auditeur rouvre et referme ses propres erreurs), cliquets Jest (`it.failing` → `it`), 48 tests d'invariants sur vrai PostgreSQL jetable en CI.

4. **Design inclusif remarquable** : voice-first pour analphabètes (Tata Nanti Lou, 137 clips pré-cachés), mode soleil (contraste renforcé pour marchés en plein jour), 3 confits visuels exclusifs, cible tactile ≥ 44 px testée CI, haptique, taille texte ajustable, WebAuthn/passkeys.

5. **Offline-first pour l'argent réel** : IndexedDB durable avec file `caisse_outbox` + `caisse_dead`, idempotence `crypto.randomUUID()`, distinction 4xx (lettre morte) vs 5xx (transitoire), atomicité transactionnelle, CAP=5 retries, mutex de refresh session unique (prévient la révocation serveur).

## 4. Points d'amélioration critiques

### Top 5 problèmes critiques

1. **3 cibles de déploiement concurrentes** (Render / OVH / Azure) — `ci/README.md` documente explicitement : « le dépôt contient deux chaînes de déploiement concurrentes (Render statique vs serveur SSH/Docker julaba.online) et rien ne prouve laquelle sert réellement la production ». `azure-pipelines.yml` ajoute une 3ème cible (Azure). À trancher en P1.

2. **14 vulnérabilités npm prod non patchées** : multer DoS × 4 CVEs, js-yaml DoS, picomatch ReDoS, qs DoS, react-router high, tmp path traversal × 2. `npm audit fix` disponible, overrides existants dans `package.json` insuffisants (lockfile à régénérer).

3. **API keys partenaires stockées EN CLAIR en DB** (table `api_keys`, colonne `key`) — incohérence avec le hash HMAC-SHA256 salé des refresh tokens. Vulnérabilité SEC-011 P1.

4. **Migrations TypeORM désactivées en prod** (`DB_MIGRATIONS_RUN=false` dans `render.yaml`) suite à l'incident du 18/09/2026 (`caisse_transaction_status_enum already exists`). Schéma reconstruit par `synchronize` + `DbInitService` idempotent — **3 doctrines parallèles** (SCHEMA-01/02/03 P1 architecture ouverts).

5. **Absence d'artéfacts standard open-governance** : pas de `README.md` à la racine, pas de `LICENSE` (projet `UNLICENSED`), pas de `CHANGELOG.md` formel, pas de tags semver (1 seul tag `pilote-latest`), pas de `backend/.env.example`, pas de `docs/POLITIQUE-CONFIDENTIALITE.md` (loi ivoirienne n°2013-450).

## 11. Conclusion

Le projet julaba-app est **remarquablement gouverné pour un pilote** : Constitution formalisée, ADR standardisés, registre de dette à 20 révisions avec auto-correction, bus de coordination IA-IA-humain, cliquets Jest, 48 tests d'invariants sur vrai Postgres, garde-fous exécutables en CI. L'auto-audit honnête (registre qui rouvre et referme ses propres erreurs, ADR qui corrige ses « affirmations fausses ») est **unique** à cette maturité de projet.

Les faiblesses sont concentrées sur **l'absence d'artéfacts standard de gouvernance open-source** (README, LICENSE, CHANGELOG, tags semver), quelques dettes documentaires (`GUIDE_DEPLOIEMENT` périmé, contradictions DOC-01/02), 14 vulnérabilités npm prod non patchées, et un retard de fusion main↔branche de travail. La conformité RGPD est **solide techniquement** (chiffrement, anonymisation prouvée, fin du takeover 0000) mais **lacunaire juridiquement** (pas de politique de confidentialité visible, pas de registre des traitements). La conformité licences est **bonne sur les dépendances majeures** (toutes permissives) mais **absente sur le projet lui-même** (UNLICENSED) — avec un cas d'école de gestion proactive du risque Sherpa-ONNX/cc-by-nc-4.0.

**Score final : 73/100** — pilote solide et gouverné, prêt pour le terrain, à fiabiliser sur l'open-governance avant passage à l'échelle. **Autorise la livraison PROD sous conditions** (≥ 60/100 requis).
